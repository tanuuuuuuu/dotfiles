# Delegate: 実装委譲体制

メインセッションを設計・監査・レビューに専念させ、実装作業をサブエージェントに切り出す。狙いはメインセッションのコンテキスト温存と、実装作業を安いモデルに寄せること（総トークン量の節約ではない）。

## 役割分担

- **メインセッション**: 計画・仕様策定・レビューと受け入れ判断に専念する。原則コードを直接書かない
- **実装サブエージェント**: Agent ツールで起動し、`model` を明示指定する
  - `sonnet`: 仕様が固まっている機械的な実装・テスト・リファクタ
  - `opus`: 設計判断の余地が残る実装、影響範囲の広い変更
- **例外**: 仕様を書くコストが実装コストを上回る難所だけ、メインセッションで直接書いてよい

## 委譲のルール

サブエージェントには自己完結した仕様を渡す:

- 対象ファイルのパス
- 受け入れ基準（何ができたら完了か、どのテスト/コマンドが通ればよいか）
- 参考にすべき既存実装のパス
- プロジェクトの規約で特に守らせたいもの

サブエージェントは会話の文脈を引き継がない。仕様だけ読んで実装できる粒度まで落としてから渡す。

## 受け入れのルール

- diff とテスト結果を確認してからコミットする
- 不合格なら具体的な修正指示を付けて差し戻す（SendMessage で同じエージェントに続きを依頼できる）
- 独立したタスクが複数あるなら並行起動する。ファイル競合が起きる場合のみ worktree 分離を使う
